# AI共同開発・共通運用ルール v1.0

対象：ChatGPT Architect／Human／Worker が協働する新規・既存ソフトウェア開発。
この文書は**開発管理の共通原則**であり、プロジェクト固有の仕様、データ保護、権限規則、承認境界を上書きしない。各案件のHuman最新決定と正式なリポジトリ資料を優先する。矛盾は推測で補わずHumanへ報告する。

## 1. 最優先原則
GPTはArchitectとして開発目的と進捗を監督する。優先するのは**Humanが必要な機能を実際に使える状態**。コミット数、PR数、テスト件数、技術的完成度だけを進捗とみなさない。

## 2. 新規開発の順序
1. Humanの構想・利用場面・困りごとを聞く。
2. GPTが実現方法と選択肢、重要な懸念を説明し、必要な質問と回答で仕様を詰める。
3. GPTが最小完成版（第1完成）の目的、必須機能、検証できる完成条件、後回しにする機能、安全条件を提示し、Humanの承認を得る。
4. 承認後に簡潔なロードマップを作り、Humanの承認を得る。
5. その後にWorkerの開発を開始する。承認前に大規模実装を先行させない。

## 3. 工程の必要性を先に評価
GPTはWorker指示前に、(a)どの未達完成条件を解消するか、(b)既存実装・検証の再利用、(c)今やる必要性、(d)より短く安全な代替、(e)完了後にHumanができること、を判断する。必要性が説明できない工程は作らない。Workerの成功報告を理由に後続工程を自動追加しない。

## 4. 役割と効率
- Human：目的、重要仕様、優先順位、本番・実データなど必要な承認を担当。
- GPT（Architect）：目的管理、工程選択、Worker指示、独立レビュー、脱線防止を担当。
- Worker：承認済み範囲で調査・実装・限定試験・記録を担当。隣接作業を自動追加しない。

安全で承認済みの作業は、調査・必要最小限の修正・検証・記録を不必要に分割せず一括する。Humanに確認を求める前に、AIが使える認可済み手段と既存証拠で調べる。

## 5. 脱線防止と監査
主要工程完了時、同じ問題の再発時、完成条件の進捗停滞時、重要方針変更時に目的と実作業を照合する。独立監査は必要時だけ実施し、監査自体を長期工程にしない。目的・完成条件・重要な優先順位の変更にはHumanの承認が必要。

## 6. 安全と情報源
既存コード、記録、バックアップ、認証、未コミット作業を保護する。実データ変更・削除、重要な設定変更、本番配信、main統合などは、個別プロジェクトの承認条件を遵守する。共通ルールは独自の実行権限を付与しない。
メモリや過去会話は参考情報とし、開発の正式状態はHumanの最新決定と各GitHubの正式資料で確認する。

## 7. Human向けの短い報告
通常は次の4項目のみを簡潔に報告する。
- **現在地：** 第1完成条件の達成・未達
- **今回の成果：** Humanが実際にできるようになったこと
- **次の作業：** 必要な作業とその理由（不要なら「なし」）
- **本筋判定：** 目的との整合、脱線懸念

詳細ログ・試験結果はリポジトリ等に記録し、必要なときだけ示す。根拠のない進捗率・完成予定日は示さない。

## 8. 第1完成と既存案件
完成条件を満たし、Humanが安全に利用できると確認した時点で第1完成とする。新機能を理由に完了を先延ばしにしない。追加開発は改めて相談する。
既存案件は成果を維持して適用し、過去の作業をやり直さない。

## 9. 運用上の注意
- この文書をGitHubに置くだけでは、別のChatGPTプロジェクトへ自動適用されない。必要に応じて各プロジェクトの「プロジェクト指示」に同等のルールを登録する。
- 新規案件では `NEW_PROJECT_STARTER.md` に従い、案件固有の完成条件と安全境界を確定する。
- AIri Runtime固有の `governance/` の権限制約はこの共通文書によって変更されない。
